Architecture Path

系统架构设计不是从技术选型开始，而是从设计理由开始。

先把业务目标、质量属性和约束讲清楚，再形成结构、验证权衡、记录决策。这样团队看到的不是一张静态架构图，而是一条可以被复盘和演进的设计链路。

01 质量属性场景 把性能、可用性、安全性、可维护性写成可验证场景。 02 属性驱动设计 用质量属性和约束驱动模块拆分，而不是先画组件。 03 C4 模型 从上下文到容器、组件、代码层层表达系统结构。 04 4+1 视图模型 补齐逻辑、开发、进程、物理和场景视角。 05 ATAM 检查关键权衡、敏感点和风险点是否成立。 06 架构决策记录 把上下文、备选方案、决定和后果沉淀下来。

Problem Playbook

先判断问题类型，再选择方法。

这张地图不是为了收藏概念，而是训练你形成稳定的拆解动作：看清问题、拆出约束、提出假设、验证判断、沉淀复盘。每次遇到复杂问题，都先把它放进一个问题类型里。

我不知道真正的问题是什么

用户说想要一个功能，但你不确定背后的动机、场景和阻力。

用户访谈 JTBD 五个为什么 How Might We
训练你从表面需求回到真实目标。

方案很多，但不知道怎么取舍

团队同时提出多个方向，争论很久却没有统一的评价标准。

决策矩阵 RICE Kano 模型 MoSCoW
训练你把感觉判断变成可复盘的决策标准。

业务复杂，系统不知道怎么拆

一个需求牵涉多个服务、角色、数据流和质量要求，单靠架构图讲不清楚。

质量属性场景 属性驱动设计 C4 模型 ATAM 架构决策记录
训练你解释设计理由，而不是只展示最终结构。

方向不确定，担心做完才发现错了

你有一个想法，但不知道用户是否需要、指标是否会变化、关键假设是否成立。

假设映射 低保真原型 精益创业 A/B 测试 HEART
训练你用证据降低不确定性，而不是用投入证明自己。

交付推进混乱，责任和节奏不清

目标已经明确，但跨团队协作、版本边界、依赖风险和决策责任不断卡住。

PRD 里程碑计划 风险清单 RAPID 上线复盘
训练你把复杂协作拆成责任、节奏和反馈闭环。

# 01

发现

用户访谈

通过结构化访谈理解用户真实场景、动机与阻力，是需求发现阶段最基础也最有效的方法。

# 02

发现

用户旅程地图

把用户在任务完成过程中的关键触点、情绪变化与断点可视化，帮助团队识别机会点。

# 03

发现

同理心地图

从"所见、所闻、所想、所感"四个维度还原用户，避免团队停留在表面反馈。

# 04

发现

JTBD

从用户试图完成的任务出发定义需求，帮助团队从"功能视角"切换到"任务视角"。

# 05

发现

五个为什么

持续追问问题背后的问题，逼近根因，避免团队把症状误当作真正要解决的需求。

# 06

发现

How Might We

把洞察转成开放但可行动的问题表达，为后续方案生成创造更好的起点。

# 07

规划

价值主张画布

把用户任务、痛点、收益与产品提供的价值对应起来，校验方案是否真正对位。

# 08

规划

故事地图

用用户行为主线组织需求，帮助团队同时看清全局体验和版本切分。

# 09

规划

服务蓝图

把前台体验、后台流程、支撑系统放到一张图上，识别服务断点与协同成本。

# 10

规划

RICE

用影响范围、预期收益、信心与投入成本来排序，适合处理资源有限时的取舍问题。

# 11

规划

Kano 模型

区分基本型、期望型和兴奋型需求，帮助团队知道哪些能力值得优先投入。

# 12

规划

MoSCoW

把需求拆成必须有、应该有、可以有和这次不做，用于推进版本协同与范围控制。

# 13

设计

领域驱动设计

围绕业务领域建模，把复杂业务概念、边界上下文和系统实现连接起来，适合处理高复杂度系统。

# 14

设计

C4 模型

用上下文、容器、组件和代码四层视角描述架构，帮助团队把系统结构讲清楚、画清楚。

# 15

设计

事件风暴

通过业务事件把流程、规则和角色快速摊开，帮助团队在需求与系统设计之间建立共同语言。

# 16

验证

低保真原型

在投入开发前快速验证信息架构和交互路径，尽早暴露方向性问题。

# 17

验证

可用性测试

观察真实用户完成任务的过程，识别体验断点、理解偏差和操作成本。

# 18

验证

A/B 测试

在真实流量中对比方案表现，用数据支持设计与增长决策。

# 19

交付与增长

PRD

把目标、范围、规则、边界和验收标准写清楚，是复杂协作中的核心对齐文档。

# 20

交付与增长

里程碑计划

把目标拆解成阶段节点、交付物与责任关系，确保团队在节奏上对齐。

# 21

交付与增长

Scrum

通过固定节奏的迭代、角色分工与仪式安排，把需求拆进 Sprint 持续交付，适合团队在不确定性中稳定推进。

# 22

交付与增长

上线复盘

围绕目标达成、偏差原因与后续动作做复盘，让交付结束变成下一轮优化的起点。

# 23

交付与增长

北极星指标

用一个最能代表长期价值的指标统一团队关注点，避免局部优化。

# 24

交付与增长

OKR

把战略目标与可衡量结果连接起来，让跨团队协作建立在更清晰的方向之上。

# 25

交付与增长

影响地图

从业务目标出发，串联参与者、行为变化与产品能力，帮助团队看清因果链条。

# 26

交付与增长

风险清单

把依赖、资源、技术、流程与认知风险提前暴露出来，降低交付后期的不确定性。

# 27

规划

决策矩阵

把多个可选方案放到同一套评估维度下打分对比，帮助团队在信息不完整时做出更透明、更可复盘的决策。

# 28

设计

技术方案文档

用结构化文档把问题背景、可选方案、技术对比和建议写清楚，让技术决策从口头讨论变成可追溯的书面判断。

# 29

交付与增长

RAPID

明确每个决策中谁提建议、谁提供输入、谁有否决权、谁最终拍板，避免责任模糊导致决策卡住或反复。

# 30

设计

质量属性场景

把性能、可用性、安全性、可维护性等抽象诉求写成可验证场景，让架构设计先回答为什么需要这样设计。

# 31

设计

ATAM

用场景和质量属性分析架构取舍，识别风险点、敏感点和权衡点，适合解释一个架构为什么值得采用。

# 32

设计

4+1 视图模型

用逻辑、开发、进程、物理和场景五个视角描述系统，避免架构图只展示模块却解释不了运行和部署。

# 33

设计

架构决策记录

把关键架构决策、上下文、备选方案和后果记录下来，让后来者理解当时为什么做这个选择。

# 34

设计

arc42

用固定章节组织架构背景、约束、构建块、运行时、部署、质量需求和风险，适合系统化写架构设计。

# 35

设计

康威定律

提醒架构边界会受到组织沟通结构影响，设计系统时也要同时设计团队边界、接口和协作方式。

# 36

规划

双钻模型

用发现、定义、发展、交付四个阶段组织发散与收敛，帮助团队从模糊机会走向清晰方案。

# 37

发现

设计思维

围绕同理、定义、创意、原型和测试推进创新，把人的真实需求放在方案形成之前。

# 38

规划

机会解决方案树

从结果指标向下拆出机会、解决方案和实验，让产品探索围绕可验证机会展开。

# 39

验证

精益创业

用构建、测量、学习循环验证商业和产品假设，尽早决定坚持、调整或放弃。

# 40

验证

假设映射

把方案背后的关键假设按重要性和证据强弱排序，优先验证最危险的未知。

# 41

验证

HEART

用幸福感、参与度、采用率、留存和任务成功五类指标衡量用户体验质量。

# 42

交付与增长

AARRR

用获客、激活、留存、收入和推荐拆解增长漏斗，帮助团队定位增长瓶颈。

# 43

设计

属性驱动设计

从架构驱动因素和质量属性出发逐层分解系统，用设计概念解释每个模块和边界的来源。
