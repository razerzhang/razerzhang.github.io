Skill 不是外挂，而是 Agent 的组织方式

Skill 这件事最近在企业里很热。很多团队都在说，业务流程可以被拆成一个个 Skill，Agent 之所以开始“能干活”，也是因为有了 Skill。 这类说法不算错，但大多只说现象，没有说清本质。我的判断是：Skill 不是给模型额外挂了一个能力包，而是在重新组织 Agent 所需的上下文。 换句话说，Skill 的核心价值不在“知识更多了”，而在“模型终于能在正确的时候拿到正确的知识、工具和执行约束”。 一、Skill 到底是什么 如果从字面理解，skill 是“技能”。但在 Agent 系统里，它并不是抽象能力，而更像一个可被模型按需调用的任务单元。一个完整的 Skill 往往包含四部分内容： 任务适用范围：它解决什么问题，不解决什么问题。 操作说明：模型应该按什么步骤完成任务。 依赖知识：完成任务需要知道哪些背景信息、规则和约束。 可调用工具：模型在执行过程中能调用哪些脚本、接口或系统能力。 因此，Skill 不是单纯的 prompt，也不是单纯的 tool，更不是一段静态知识。它是把目标、方法、知识和工具组织在一起，交给模型按需装载的一种结构。 二、为什么 Skill 会突然变得重要 大模型能力变强之后，一个更现实的问题暴露出来了：模型不是不会推理，而是经常在错误的上下文里推理。 很多 Agent 失败，并不是因为模型“智商不够”，而是因为它在执行任务时面临三类典型问题： 不知道当前任务到底该用哪一套规则。 知道规则，但不知道该调用哪个工具。 工具和知识分散在不同地方，模型很难把它们稳定地拼起来。 这也是为什么很多团队做了大量 context engineering，效果却依然不稳定。问题不只是“给模型更多上下文”，而是“如何把真正相关的上下文，以可执行的方式组织进去”。 Skill 的出现，正是为了解这个问题。 三、为什么只靠 RAG 不够 很多系统最早的方案是 RAG：先检索，再把召回内容塞进上下文，让模型回答或执行。 RAG 很有价值，但它更擅长解决“知道什么”，不擅长解决“该怎么做”。一旦任务进入执行阶段，RAG 往往会暴露三个短板： 检索结果偏知识片段，不是完整操作单元。模型拿到了说明书，却不一定拿到了工具。 召回稳定性不足。相似问题在不同轮次里，可能召回出不同材料，导致执行结果波动。 工具和知识分离。知识在向量库里，工具在代码里，模型需要自己把两者拼接起来，这一步往往最不稳定。 这正是 Skill 更有穿透力的地方。Skill 把知识和工具预先绑定，让模型在加载某个任务单元时，同时获得： 这件事该怎么做 这件事能用什么工具做 这件事有哪些约束不能违反 从这个角度看，Skill 不是替代 RAG，而是在很多执行型任务里，把 RAG 的“知识召回”推进成“可执行上下文装配”。 四、Skill 真正解决的，是上下文组织问题 很多人把 Skill 理解成“封装经验”，这没有错，但还不够精确。更准确的说法是：Skill 是一种上下文压缩与按需披露机制。
