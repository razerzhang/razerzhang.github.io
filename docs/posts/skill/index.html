Skill

企业里很多人把 Skill 当成 AI 落地的终极形态，但真正有价值的不是 Skill 数量，而是你是否把稳定能力、上下文边界和协作方式设计清楚了。

最近在公司里，Skill 这个词非常火。很多人会说：以后不用做系统了，直接把业务流程封装成 Skill 就行；也有人会说，Agent 的能力边界就是 Skill 的数量，Skill 越多，AI 就越强。

这类说法不能说全错，但很容易把事情讲得过于简单。

我现在的看法是：Skill 很重要，但它不是一切。
它更像一种能力封装方式，而不是业务复杂度的终极容器。把所有问题都塞进 Skill，最后往往会得到一个看起来灵活、实际上难维护的系统。

Skill 到底是什么

如果用最朴素的话来讲，Skill 就是把一段可复用的能力，以 AI 更容易调用的形式沉淀下来。它通常包含几部分：

  • 这项能力是干什么的
  • 在什么场景下该调用
  • 输入输出分别是什么
  • 执行时依赖哪些工具、规则或上下文

比如“生成周报”“读取 PR 并做风险审查”“把会议纪要整理成固定格式”，这些都适合被封装成 Skill。因为它们有相对稳定的触发条件、可预期的执行路径，以及明确的产出标准。

所以 Skill 的核心价值，不是“让 AI 会更多东西”，而是让原本靠人临场发挥的动作，变成可复用、可传递、可约束的能力模块。

为什么企业里会突然这么火

我觉得 Skill 爆火，本质上是因为它刚好卡在企业落地 AI 的几个痛点上。

第一，它降低了复用成本。以前一个好用的 Prompt 往往掌握在少数人手里，复制粘贴之后效果还不稳定。做成 Skill 之后，至少可以让更多人复用同一套能力。

第二，它降低了协作门槛。业务同学不一定懂模型原理，也不关心底层推理过程，但他们能理解“这个 Skill 可以帮我做合同摘要”“那个 Skill 可以帮我查数据并生成邮件”。

第三，它给平台化提供了抓手。对平台建设者来说，Skill 是一个天然的抽象层。它既比“自由对话”更可控，又比“写死流程”更灵活，适合在企业内部快速推广。

从这个角度讲，Skill 的流行不是偶然。它确实是 AI 工程化过程里一个很自然的中间层。

但为什么我觉得 Skill 不是一切

问题在于，很多团队在看到 Skill 有用之后，会开始把所有问题都往 Skill 上靠。最后会出现三种常见误区。

误区一：把业务流程等同于 Skill

一个 Skill 适合承载的是“稳定能力”，不是整个复杂流程。

比如“从 Jira 拉取需求，结合代码变更分析风险，再同步到飞书，并根据负责人状态决定是否升级提醒”，这种事情本质上已经不是一个单一能力，而是一段多状态、多角色、多系统协同的流程。

如果强行把它塞进一个 Skill，短期内也许能跑起来，但后面会越来越难维护。因为你真正面对的问题不是“AI 会不会做”，而是：

  • 流程状态如何管理
  • 失败后如何重试
  • 权限边界如何控制
  • 中间结果如何审计
  • 不同节点由谁负责确认

这些问题本质上属于工作流、系统编排和组织协作，不属于 Skill 本身。

所以我更倾向于把 Skill 理解成“流程中的能力节点”，而不是“流程本身”。

误区二：Skill 越多，Agent 越强

很多平台都喜欢强调自己的 Skill 市场、Skill 数量、Skill 覆盖范围，好像数量上去之后，Agent 就会自然变聪明。

但现实并不是这样。

Skill 太多，反而可能让模型更难选择。名字相似、职责重叠、边界模糊的 Skill 越多，调用就越容易混乱。最终结果不是能力增强，而是路由成本变高、稳定性下降。

真正重要的不是 Skill 的数量，而是 Skill 的设计质量：

  • 这个 Skill 的职责是否单一
  • 调用条件是否明确
  • 是否有稳定的输入输出约定
  • 是否能和其他 Skill 自然组合

少量清晰、边界分明的 Skill，往往比一堆大而全的 Skill 更有价值。

误区三：Skill 可以替代上下文工程

很多人以为，只要把 Skill 写好了，AI 就会自动把事情做好。但实际上，Skill 只是能力说明书，真正影响效果的，往往还是上下文。

同样一个“写周报”的 Skill，如果没有清晰的工作记录、没有统一的输出模板、没有团队约定的表达风格，那结果还是会飘。

换句话说，Skill 解决的是“会不会做”的问题，上下文工程解决的是“做得像不像、稳不稳”的问题。

我越来越觉得，AI 落地最难的部分不在模型，而在上下文组织。你有没有把业务术语讲清楚？有没有把数据源打通？有没有把成功标准定义出来？这些才是决定效果上限的东西。

什么样的能力适合做成 Skill

我目前判断一个能力是否适合 Skill 化，主要看四个标准。

1. 场景是否高频

低频、一次性的事情，不值得专门封装。真正适合做 Skill 的，通常是会反复出现、多人都需要用的场景。

2. 边界是否稳定

如果一个任务的目标、输入、输出一直在变，那更适合先通过人工探索，等模式稳定后再沉淀成 Skill。

3. 结果是否可校验

一个好的 Skill，最好有相对明确的验收标准。比如格式是否正确、字段是否齐全、结论是否覆盖关键风险点。否则就很难持续优化。

4. 是否值得复用

有些事情虽然能做成 Skill，但复用价值很低。那它更适合保留在 Prompt 或临时任务里，而不是进入平台资产。

总结下来就是一句话：高频、稳定、可校验、值得复用的能力，最适合 Skill 化。

我认为一个好 Skill 应该长什么样

在设计 Skill 的时候，我现在会特别关注下面几个点。

职责单一

一个 Skill 最好只解决一个问题。不要把“读取信息 + 分析 + 决策 + 执行”全部塞到一起。职责越单一，复用性越高，也越容易调试。

触发条件明确

要让调用方知道“什么时候该用它，什么时候不该用它”。如果一个 Skill 什么都能做，基本等于什么都做不好。

输入输出标准化

哪怕只是文本输入，也尽量约定结构。输入越稳定，输出越可控；输出越可控，后续流程越容易接住。

有失败策略

真实业务里，失败不是例外，而是常态。Skill 需要考虑拿不到数据怎么办、权限不足怎么办、外部接口超时怎么办，而不是默认每次都成功。

能被观察和迭代

如果一个 Skill 的调用记录、成功率、失败原因都看不到，那它很难成为真正的生产资产。平台化不是把 Prompt 收集起来，而是要形成反馈闭环。

Skill、Workflow 和 Agent 之间的关系

这三者很容易被混着说，但我越来越觉得，它们应该分层理解。

  • Skill：解决单点能力复用的问题
  • Workflow：解决步骤编排、状态流转和系统协同的问题
  • Agent：解决在不确定环境下做动态选择和组合的问题

Skill 像工具，Workflow 像流水线，Agent 像调度者。

如果把这个分层想清楚，很多讨论就不会跑偏。不是所有场景都需要 Agent，也不是所有流程都该被做成 Skill。大多数时候，真正有效的架构是：用 Workflow 承载确定性，用 Skill 提供能力块，用 Agent 只处理那些确实需要判断和动态规划的部分。

对我自己的提醒

这段时间做平台、和业务方沟通之后，我越来越警惕一种倾向：只要 AI 能参与，就急着把它抽象成一个“高级能力模块”。这很容易让人产生一种进展很快的错觉，但实际上，很多复杂度只是被藏起来了。

真正扎实的建设，不是做出多少个 Skill，而是回答清楚几个问题：

  • 哪些能力值得沉淀
  • 哪些流程应该系统化
  • 哪些判断必须留给人
  • 哪些环节需要审计、权限和责任归属

这些问题不解决，Skill 只会变成另一种形式的技术债。

结语

Skill 确实是 AI 落地里很重要的一层，我自己也非常认可它的价值。但如果因此得出“Skill 就是一切”，那就把问题看窄了。

我更愿意把它看成企业 AI 基础设施中的一个零件。它很关键，但它必须和上下文工程、流程编排、权限治理、评估体系一起工作，才能真正产生长期价值。

所以，对我来说，Skill 不是终点。
它只是把能力沉淀下来的开始。
