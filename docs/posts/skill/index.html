Skill 不是外挂，而是 Agent 的组织方式

Skill 的价值不在于给模型外挂能力，而在于把目标、方法、知识、工具和约束整理成可按需加载的任务单元，让 Agent 在正确上下文里稳定执行。

Skill 这件事最近在企业里很热。很多团队都在说，业务流程可以被拆成一个个 Skill，Agent 之所以开始“能干活”，也是因为有了 Skill。

这类说法不算错，但大多只说现象，没有说清本质。我的判断是：Skill 不是给模型额外挂了一个能力包，而是在重新组织 Agent 所需的上下文。

换句话说，Skill 的核心价值不在“知识更多了”，而在“模型终于能在正确的时候拿到正确的知识、工具和执行约束”。

如果用一个更工程化的定义来概括：

Skill = 触发条件 + 操作说明 + 依赖知识 + 可用工具 + 执行约束。

它解决的不是“模型是否聪明”，而是“模型在执行任务时，是否拿到了刚好够用、结构稳定、可以落地的上下文”。

一、Skill 到底是什么

如果从字面理解，skill 是“技能”。但在 Agent 系统里，它并不是抽象能力，而更像一个可被模型按需调用的任务单元。一个完整的 Skill 往往包含四部分内容：

  1. 任务适用范围：它解决什么问题，不解决什么问题。
  2. 操作说明：模型应该按什么步骤完成任务。
  3. 依赖知识：完成任务需要知道哪些背景信息、规则和约束。
  4. 可调用工具：模型在执行过程中能调用哪些脚本、接口或系统能力。

因此，Skill 不是单纯的 prompt，也不是单纯的 tool，更不是一段静态知识。它是把目标、方法、知识和工具组织在一起，交给模型按需装载的一种结构。

举一个更具体的例子：如果要做一个“代码审查 Skill”，它不应该只是一句“帮我 review 代码”的提示词，而应该包含：

组成部分具体内容
触发条件当用户要求检查 PR、评估代码变更、定位潜在回归时启用
操作说明先读 diff，再看相关调用链，最后按严重程度输出问题
依赖知识项目的代码规范、架构约束、测试策略、兼容性要求
可用工具git diff、测试命令、静态检查脚本、PR 评论接口
执行约束不修改无关文件，不输出没有证据的问题，不把风格偏好当 bug

这样的 Skill 才是一个可执行的任务单元。它不是让模型“知道更多”，而是让模型在代码审查这个场景里，稳定地知道应该看什么、怎么判断、能调用什么工具、哪些边界不能越过。

二、为什么 Skill 会突然变得重要

大模型能力变强之后，一个更现实的问题暴露出来了：模型不是不会推理，而是经常在错误的上下文里推理。

很多 Agent 失败，并不是因为模型“智商不够”，而是因为它在执行任务时面临三类典型问题：

  1. 不知道当前任务到底该用哪一套规则。
  2. 知道规则，但不知道该调用哪个工具。
  3. 工具和知识分散在不同地方，模型很难把它们稳定地拼起来。

这也是为什么很多团队做了大量 context engineering，效果却依然不稳定。问题不只是“给模型更多上下文”，而是“如何把真正相关的上下文，以可执行的方式组织进去”。

Skill 的出现，正是为了解这个问题。

三、为什么只靠 RAG 不够

很多系统最早的方案是 RAG：先检索，再把召回内容塞进上下文，让模型回答或执行。

RAG 很有价值，但它更擅长解决“知道什么”，不擅长解决“该怎么做”。一旦任务进入执行阶段，RAG 往往会暴露三个短板：

  1. 检索结果偏知识片段，不是完整操作单元。模型拿到了说明书，却不一定拿到了工具。
  2. 召回稳定性不足。相似问题在不同轮次里，可能召回出不同材料，导致执行结果波动。
  3. 工具和知识分离。知识在向量库里，工具在代码里，模型需要自己把两者拼接起来，这一步往往最不稳定。

这正是 Skill 更有穿透力的地方。Skill 把知识和工具预先绑定，让模型在加载某个任务单元时，同时获得：

  • 这件事该怎么做
  • 这件事能用什么工具做
  • 这件事有哪些约束不能违反

从这个角度看，Skill 不是替代 RAG，而是在很多执行型任务里，把 RAG 的“知识召回”推进成“可执行上下文装配”。

可以把三者的关系先粗略分开：

机制主要解决的问题典型短板和 Skill 的关系
RAG把相关知识找回来召回的是片段，不一定包含执行步骤和工具Skill 可以把被召回的知识组织进任务流程
Function Calling让模型调用外部能力工具太多时选择成本高，调用前缺少任务语境Skill 决定当前任务该暴露哪组工具
Skill把目标、知识、步骤、工具和约束组织成任务单元需要提前抽象场景和边界是更上层的执行上下文组织方式

所以三者不是替代关系，而是分工关系。RAG 更偏知识，Function Calling 更偏接口，Skill 更偏任务组织。

四、Skill 真正解决的，是上下文组织问题

很多人把 Skill 理解成“封装经验”，这没有错，但还不够精确。更准确的说法是：Skill 是一种上下文压缩与按需披露机制。

原因很简单。模型的上下文窗口不是无限的，工具也不可能全量注入。只要你把所有说明、规则和工具一次性塞给模型，就会出现三个后果：

  1. 上下文迅速膨胀，成本变高。
  2. 模型选错工具的概率上升。
  3. 关键信息被淹没，执行质量下降。

Skill 的常见做法是渐进式披露：

  1. 先让模型看到 Skill 的元数据，例如名称、用途、触发条件。
  2. 模型根据用户任务判断是否需要加载某个 Skill。
  3. 只有命中后，系统才进一步注入该 Skill 的详细说明、脚本和约束。

这个过程的意义不只是“省 token”，更重要的是让模型在每一步都只面对当前真正相关的信息。Agent 的稳定性，很多时候就来自这种信息分层，而不是来自更复杂的推理链。

五、为什么 Skill 会让 Agent 看起来终于“能执行”了

Agent 真正难的不是回答问题，而是把任务落到环境里。

一旦进入执行阶段，系统至少要同时满足四个条件：

  1. 模型知道目标是什么。
  2. 模型知道执行步骤是什么。
  3. 模型知道可以调用哪些工具。
  4. 模型处在一个允许试错、读取文件、运行脚本的执行环境里。

Skill 本身解决的是前 3 个问题，沙箱或运行环境解决的是第 4 个问题。两者结合之后，Agent 才从“会说”走向“会做”。

这也是为什么很多人会产生一种明显感受：有了 Skill 和沙箱环境后，Agent 好像突然可以执行任务了。其实不是模型突然变聪明了，而是系统终于把执行所需的上下文和能力组织对了。

六、Function Calling 本质上也是上下文工程

很多人把 Function Calling 视为模型的原生能力，这当然没问题。但如果从系统设计角度看，Function Calling 本质上也是上下文工程的一部分。

因为 tool 本身并不会自动被模型正确使用。系统必须回答两个问题：

  1. 哪些 tool 应该出现在当前上下文里？
  2. 它们应该以什么结构被模型看到？

如果把全部 tool 一次性提供给模型，会立刻出现两个问题：上下文膨胀，以及工具选择精度下降。也就是说，Function Calling 的难点从来不只是“定义一个 schema”，而是如何控制模型在什么场景下看到什么工具。

从这个角度看，Skill 和 Function Calling 并不冲突。Skill 更像是上层的任务组织单元，Function Calling 是底层的调用机制。前者负责决定“该加载哪组能力”，后者负责决定“具体怎么调用能力”。

七、固定结构为什么重要

当系统进入多轮调用、多工具协同时，另一个经常被忽略的问题会出现：上下文结构是否稳定。

稳定的上下文结构至少带来两个收益：

  1. 模型更容易形成一致的工具选择模式。
  2. 模型更容易利用前缀缓存，例如 KV cache，降低延迟和成本。

OpenAI 在 GPT-5.4 中引入的 tool search 就是一个典型信号：当系统拥有大量工具时，不再需要把所有工具定义一次性塞进上下文，而是让模型在需要时查找并加载具体工具定义。这说明工具可见性本身就需要被设计，而不是简单地“全量提供”。参考：Introducing GPT-5.4。

这也是为什么很多新一代 Agent 系统会强调工具分层、固定顺序和按需加载。不是为了形式好看，而是因为结构稳定本身就是性能和准确率的一部分。

因此，真正成熟的 Skill 系统通常不会追求“把所有能力都做成一个超大 Skill”，而是追求：

  • 能力拆分清晰
  • 触发条件明确
  • 装载路径稳定
  • 工具接口统一

八、Skill 的边界在哪里

当然，Skill 也不是万能的。

如果一个任务高度开放、目标模糊、执行路径极不稳定，那么 Skill 的收益会下降。因为 Skill 更适合的是那些“目标明确，但执行细节复杂”的任务，例如代码修改、数据处理、内容生成、流程操作等。

换句话说，Skill 最擅长的不是替模型思考，而是把思考和执行所需的上下文提前组织好。

所以我更愿意把 Skill 看成一种工程化手段，而不是一种神奇能力。它解决的不是模型上限问题，而是模型在真实系统中的落地问题。

更具体地说，Skill 适合三类任务：

  1. 目标清楚，但步骤较长，例如发布流程、PR 审查、数据清洗。
  2. 需要绑定工具和规则，例如读取文件、运行脚本、调用内部系统。
  3. 需要稳定复用团队经验，例如写作规范、代码规范、故障排查流程。

Skill 不太适合三类任务：

  1. 目标本身还没想清楚，只是在开放探索。
  2. 判断标准高度主观，无法沉淀成明确约束。
  3. 每次执行路径都完全不同，抽象成本高于复用收益。

九、怎么设计一个好 Skill

如果把 Skill 当成工程化产物，而不是一句提示词，那么设计 Skill 时至少要检查五件事：

  1. 触发条件是否清晰。 模型要知道什么时候该加载它，也要知道什么时候不该加载它。
  2. 输入输出是否明确。 一个 Skill 最好能说清它需要什么输入，最终应该交付什么结果。
  3. 工具集合是否最小。 只暴露完成任务真正需要的工具，避免让模型在无关工具里做选择。
  4. 约束是否可执行。 不要只写价值观式原则，要写成模型在执行时能判断的规则。
  5. 失败路径是否可恢复。 工具失败、信息缺失、权限不足时，Skill 应该告诉模型如何降级或向用户确认。

好的 Skill 不一定复杂，但一定边界清楚。它应该像一份可执行的任务说明书，而不是一段写得很漂亮的背景材料。

十、结论

关于 Skill，我的核心观点只有一句话：Skill 不是外挂，而是 Agent 的组织方式。

它之所以重要，不是因为它给模型增加了某种新天赋，而是因为它把原本零散的知识、工具、步骤和约束，整理成了模型可以按需加载、稳定执行的上下文单元。

RAG 解决的是“把知识找回来”，Function Calling 解决的是“把工具调起来”，而 Skill 解决的是“让知识、工具和流程在同一个任务单元里被正确组织”。

当这三者再和一个可执行环境结合起来时，Agent 才真正从“能回答”走向“能完成任务”。
